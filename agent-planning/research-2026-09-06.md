# Agent 技术规划：第一轮行业问题地图

调研日期：2026-09-06。用途：辅助 2026—2027 年投入讨论；不是已批准路线图。

## 结论与证据边界

综合判断：四个方向可以围绕“agent 如何长时间可靠工作、积累可复用经验，并有效分工”形成问题地图。但它们不必组成一个统一产品，也不意味着都值得# 补充研究：Agent 安全与 DeepSeek Harness

核验日期：2026-09-06。初步问题地图；未进行源码审计、攻击复现或性能测量。

## Agent 安全

暂按“保护 agent 系统及它访问的数据和外部系统”理解。用 agent 做漏洞研究、检测和响应属于另一个应用方向，是否纳入待用户确认。

公开依据：Anthropic 将可信 agent 的实践放在模型、工具、权限和环境等多个层次；MINJA 研究说明记忆污染能够影响后续会话。这支持跨层研究，但不能证明某个项目存在相同漏洞。[Trustworthy agents](https://www.anthropic.com/research/trustworthy-agents)、[MINJA](https://arxiv.org/abs/2503.03704)

建议研究矩阵（助手提出，尚未批准）：

| 层次 | 核心问题 | 与现有投入的连接 |
|---|---|---|
| 输入与意图 | 外部数据如何被误当作指令；如何识别目标偏移？ | Harness 的输入来源与执行策略 |
| 身份与权限 | 工具调用以谁的身份执行，委派能否扩大权限，撤权何时生效？ | Harness、multi-agent |
| 运行环境 | 隔离、出网、凭证、宿主与租户边界如何闭合？ | Sandbox |
| 记忆与上下文 | 污染、跨租户泄漏、来源丢失、删除后的派生内容如何处理？ | OpenViking、共享记忆 |
| 插件与工具 | 不可信插件/MCP/skill 的代码和返回内容分别能触及哪些资源？ | DeerFlow、DSH 生态 |
| 协作与恢复 | 错误是否跨 agent 传播；重试、回滚是否重复外部副作用？ | 四方向接口 |
| 验证与处置 | 如何测攻击成功、业务损失、误阻断、人工负担及撤销恢复？ | 横向评估 |

规划推断：安全既应有独立问题清单，也应成为每个方向的设计和验收条件。是否成立独立投入主线取决于用户、威胁模型和可验证差异。沙箱隔离不等同于语义授权正确，插件可替换也不等同于安全隔离。

## DeepSeek Harness

已确认是 deepseek-ai/deepseek-harness（dsh）。官方当前标注 developer preview，核心能力和 API 仍将演进。[官网](https://deepseek.com/harness/en/)、[仓库](https://github.com/deepseek-ai/deepseek-harness)

官方声明：基于 Cordis 的插件组合；模型、工具、session、sandbox、storage、loop、调度和 UI 都可替换；append-only session log 记录模型上下文和执行事件，支持轨迹检查以及恢复、分叉、搜索和回放；提供 Standard、Code、Minimal、Creator 多种模式。上述是设计与能力声明，尚未证明恢复正确性或跨任务效果。[官方介绍](https://deepseek.com/harness/en/)

对照研究待办（助手建议）：

- 插件边界与故障边界是否一致；权限和资源隔离如何实现。
- session 日志是否足以支撑恢复，哪些外部状态无法被重放。
- OpenViking 类长期上下文与 session 原始记录如何划分职责。
- 换 sandbox 或 agent loop 后，验收、安全和恢复语义是否保持。
- 不同运行模式与多 agent 协作的收益，在同模型和预算下是否稳定。

不因 DSH 的插件理念预设应迁移 DeerFlow；优先明确哪些边界值得借鉴、哪些问题需要共同实验。

## Sandbox

公开进展：AgentENV 当前强调 agentic RL 环境规模、镜像按需加载、增量快照、fork 与资源密度；CubeSandbox 强调快速启动、快照回滚、跨节点恢复及出网凭证代理。上述性能数字是项目自报，不能跨项目直接比较。[AgentENV](https://github.com/kvcache-ai/AgentENV)、[CubeSandbox](https://github.com/TencentCloud/CubeSandbox)

E2B 的 SDK 已提供暂停与快照接口；Modal 区分目录、文件系统和内存快照，内存快照仍标注 Alpha。它们展示了不同的状态与生命周期抽象，而非完全同等的恢复语义。[E2B SDK](https://github.com/e2b-dev/E2B/blob/main/packages/js-sdk/src/sandbox/index.ts)、[Modal snapshots](https://modal.com/docs/guide/sandbox-snapshots)

待研究的四条主线：

- 生命周期经济性：长时间等待模型、空闲、恢复及镜像多样性下的总成本；不只测冷启动。
- 执行状态语义：什么被快照、什么没被快照；文件、进程、外部系统副作用如何配合恢复。快照不自动撤销已发出的外部操作。
- 隔离与可用性：文件、网络、凭证和控制平面权限共同决定可执行边界；microVM 只是其中一层。
- 训练与在线负载差异：训练更关注批量环境、reset/fork 和吞吐；在线任务还关心持久工作空间、尾延迟与用户数据边界。两者能复用哪些基础设施需要测量。

安全边界研究参考 Anthropic 对不同产品采用不同隔离模式的经验，不能概括为一种技术适用所有场景。[How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)

团队候选实验：相同任务、资源约束、镜像与并发下，对比完整任务成本、P95 可工作延迟、恢复成功率及故障后的重复副作用；再决定现有社区投入是在探索不同负载，还是重复补齐同类能力。

## Memory / Context

OpenViking 将 memory、resources、skills 统一组织，采用文件系统式访问和分层上下文。Anthropic 的 context engineering 实践包括按需检索、压缩、笔记与隔离上下文。[OpenViking](https://github.com/volcengine/OpenViking)、[Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

五条问题主线：

1. 上下文供给：需要时能否以合适粒度取得有效信息；语义相关不等于对当前决策有用。
2. 经验提炼与迁移：从轨迹形成经验，同时保留适用前提，避免将偶然成功泛化。
3. 持续更新：冲突、过期、删除、并发写入、异步整理及新信息可见延迟。
4. 来源与信任：区分用户陈述、外部内容、工具证据和 agent 推断，追溯并撤销错误传播。
5. 收益评估：记忆问答更准确是否转化为真实任务表现，且能覆盖写入与整理成本。

ACE 研究上下文 playbook 的增量演进；MemoryAgentBench 将选择性遗忘纳入评估；VikingMem 和 MemForest 分别提供时间状态管理与记忆构建效率方面的研究线索。[ACE](https://arxiv.org/abs/2510.04618)、[MemoryAgentBench](https://arxiv.org/abs/2507.05257)、[VikingMem](https://arxiv.org/abs/2605.29640)、[MemForest](https://arxiv.org/abs/2605.23986)

LongMemEval-V2（2026-05）评估环境状态、工作流、陷阱和前提意识，说明评估范围已超出聊天事实回忆。但它使用预采集轨迹和固定 reader 的证据问答，不直接证明在线任务成功率。MINJA 则说明记忆污染可能跨会话影响后续行为；不能将该研究成功率套用为 OpenViking 的风险率。[LongMemEval-V2](https://arxiv.org/html/2605.12493v1)、[MINJA](https://arxiv.org/abs/2503.03704)

团队候选实验：无记忆、原始轨迹文件与搜索、结构化经验记忆三组对比；在未用于经验构建的新任务及发生变化的环境中测成功率、重复错误、成本与错误经验撤销。把 memory 组件诊断与端到端任务收益分开。

## Harness

行业问题包括跨上下文接续、故障恢复、工具与权限边界、完成判定、评估归因，以及模型升级后哪些策略应删去。Anthropic Managed Agents 分离 session 日志、harness 和 sandbox；其经验显示为旧模型添加的 workaround 可能随模型改进失去价值。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)

长任务工程经验强调增量工作与验证；生成者自评或独立评价器都需要检查准确性。[Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)

Harness-Bench（2026-05）在共享环境和预算下研究模型与 harness 配对，提示不能将最终能力全归因于模型。DeerFlow 已集成 sandbox、memory、skills 与 subagents；功能存在不代表跨组件可靠性已被证明。[Harness-Bench](https://arxiv.org/abs/2605.27922)、[DeerFlow](https://github.com/bytedance/deer-flow)

团队候选实验：固定模型，注入工具超时、进程退出、上下文压缩、环境重建等故障，检查实际产物、恢复后约束保留和重复工作；更换模型后做策略消融，识别过时策略。

## Multi-agent

关键问题是任务结构与协调方式是否匹配。可独立广度搜索有实践收益；紧耦合和强共享状态工作可能承担较多沟通成本。Anthropic 的 research 系统案例不能单独证明纯拓扑收益，因为配置和计算投入也不同。[Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)

Towards a Science of Scaling Agent Systems v3（2026-04）在 260 个配置、6 个基准下显示协作效果依任务而异；工具密集型任务开销、单 agent 能力饱和及错误传播都是重要变量。MAST 将协作失败分成设计、agent 间不一致、验证与终止等类别。[Scaling Agent Systems](https://arxiv.org/abs/2512.08296v3)、[MAST](https://sites.google.com/berkeley.edu/mast)

团队候选问题：什么时候委派、给谁、传递什么上下文、如何协调写入、如何识别没有进展、何时停止或退回单 agent。

实验基线：普通单 agent、增加预算的单 agent、多 agent；分别比较等成本、等时间、等质量，区分并行加速、上下文隔离、专业能力与单纯增加计算的收益。

## 跨方向的评估基础

AgentCompass 将 benchmark、harness、environment 分开。Anthropic 的环境噪声研究表明，资源配置能影响 agentic benchmark 成绩，因此必须记录环境和资源执行策略。[AgentCompass](https://arxiv.org/abs/2607.13705)、[Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)

建议统一任务与轨迹、成功标准、模型版本、预算、环境配置、记忆历史与验收器；在重复运行中做消融和故障归因。已有基础可复用，不预设要新建一个框架。

## 待讨论的规划假设

以下均为研究后的候选方向，未形成团队共识：

- 可恢复且可验证的长任务执行：跨 sandbox 与 harness，以中断后仍正确交付为目标。
- 有效且可纠错的经验积累：跨 OpenViking 与实际 harness，以新任务收益及环境变化后的适应为目标。
- 按任务结构分配协作与预算：跨 multi-agent、harness、sandbox 分叉和共享知识，以同预算净收益为目标。

关键接口假设：sandbox 恢复不能使 session 和记忆仍指向未来状态；分支经验写入共享记忆应保留适用范围与证据；任务完成需要外部验收支撑。这些是建议验证的问题，不是已经证明的产品缺陷。

3. 持续更新：冲突、过期、删除、并发写入、异步整理及新信息可见延迟。
4. 来源与信任：区分用户陈述、外部内容、工具证据和 agent 推断，追溯并撤销错误传播。
5. 收益评估：记忆问答更准确是否转化为真实任务表现，且能覆盖写入与整理成本。

ACE 研究上下文 playbook 的增量演进；MemoryAgentBench 将选择性遗忘纳入评估；VikingMem 和 MemForest 分别提供时间状态管理与记忆构建效率方面的研究线索。[ACE](https://arxiv.org/abs/2510.04618)、[MemoryAgentBench](https://arxiv.org/abs/2507.05257)、[VikingMem](https://arxiv.org/abs/2605.29640)、[MemForest](https://arxiv.org/abs/2605.23986)

LongMemEval-V2（2026-05）评估环境状态、工作流、陷阱和前提意识，说明评估范围已超出聊天事实回忆。但它使用预采集轨迹和固定 reader 的证据问答，不直接证明在线任务成功率。MINJA 则说明记忆污染可能跨会话影响后续行为；不能将该研究成功率套用为 OpenViking 的风险率。[LongMemEval-V2](https://arxiv.org/html/2605.12493v1)、[MINJA](https://arxiv.org/abs/2503.03704)

团队候选实验：无记忆、原始轨迹文件与搜索、结构化经验记忆三组对比；在未用于经验构建的新任务及发生变化的环境中测成功率、重复错误、成本与错误经验撤销。把 memory 组件诊断与端到端任务收益分开。

## Harness

行业问题包括跨上下文接续、故障恢复、工具与权限边界、完成判定、评估归因，以及模型升级后哪些策略应删去。Anthropic Managed Agents 分离 session 日志、harness 和 sandbox；其经验显示为旧模型添加的 workaround 可能随模型改进失去价值。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)

长任务工程经验强调增量工作与验证；生成者自评或独立评价器都需要检查准确性。[Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)

## Multi-agent

关键问题是任务结构与协调方式是否匹配。可独立广度搜索有实践收益；紧耦合和强共享状态工作可能承担较多沟通成本。Anthropic 的 research 系统案例不能单独证明纯拓扑收益，因为配置和计算投入也不同。[Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)

Towards a Science of Scaling Agent Systems v3（2026-04）在 260 个配置、6 个基准下显示协作效果依任务而异；工具密集型任务开销、单 agent 能力饱和及错误传播都是重要变量。MAST 将协作失败分成设计、agent 间不一致、验证与终止等类别。[Scaling Agent Systems](https://arxiv.org/abs/2512.08296v3)、[MAST](https://sites.google.com/berkeley.edu/mast)

## Agent 安全

暂按“保护 agent 系统及它访问的数据和外部系统”理解。用 agent 做漏洞研究、检测和响应属于另一个应用方向，是否纳入待用户确认。

公开依据：Anthropic 将可信 agent 的实践放在模型、工具、权限和环境等多个层次；MINJA 研究说明记忆污染能够影响后续会话。这支持跨层研究，但不能证明某个项目存在相同漏洞。[Trustworthy agents](https://www.anthropic.com/research/trustworthy-agents)、[MINJA](https://arxiv.org/abs/2503.03704)

建议研究矩阵（助手提出，尚未批准）：

| 层次 | 核心问题 | 与现有投入的连接 |
|---|---|---|
| 输入与意图 | 外部数据如何被误当作指令；如何识别目标偏移？ | Harness 的输入来源与执行策略 |
| 身份与权限 | 工具调用以谁的身份执行，委派能否扩大权限，撤权何时生效？ | Harness、multi-agent |
| 运行环境 | 隔离、出网、凭证、宿主与租户边界如何闭合？ | Sandbox |
| 记忆与上下文 | 污染、跨租户泄漏、来源丢失、删除后的派生内容如何处理？ | OpenViking、共享记忆 |
| 插件与工具 | 不可信插件/MCP/skill 的代码和返回内容分别能触及哪些资源？ | DeerFlow、DSH 生态 |
| 协作与恢复 | 错误是否跨 agent 传播；重试、回滚是否重复外部副作用？ | 四方向接口 |
| 验证与处置 | 如何测攻击成功、业务损失、误阻断、人工负担及撤销恢复？ | 横向评估 |

规划推断：安全既应有独立问题清单，也应成为每个方向的设计和验收条件。是否成立独立投入主线取决于用户、威胁模型和可验证差异。沙箱隔离不等同于语义授权正确，插件可替换也不等同于安全隔离。

## Sandbox

公开进展：AgentENV 当前强调 agentic RL 环境规模、镜像按需加载、增量快照、fork 与资源密度；CubeSandbox 强调快速启动、快照回滚、跨节点恢复及出网凭证代理。上述性能数字是项目自报，不能跨项目直接比较。[AgentENV](https://github.com/kvcache-ai/AgentENV)、[CubeSandbox](https://github.com/TencentCloud/CubeSandbox)

E2B 的 SDK 已提供暂停与快照接口；Modal 区分目录、文件系统和内存快照，内存快照仍标注 Alpha。它们展示了不同的状态与生命周期抽象，而非完全同等的恢复语义。[E2B SDK](https://github.com/e2b-dev/E2B/blob/main/packages/js-sdk/src/sandbox/index.ts)、[Modal snapshots](https://modal.com/docs/guide/sandbox-snapshots)

待研究的四条主线：

- 生命周期经济性：长时间等待模型、空闲、恢复及镜像多样性下的总成本；不只测冷启动。
- 执行状态语义：什么被快照、什么没被快照；文件、进程、外部系统副作用如何配合恢复。快照不自动撤销已发出的外部操作。
- 隔离与可用性：文件、网络、凭证和控制平面权限共同决定可执行边界；microVM 只是其中一层。
- 训练与在线负载差异：训练更关注批量环境、reset/fork 和吞吐；在线任务还关心持久工作空间、尾延迟与用户数据边界。两者能复用哪些基础设施需要测量。

安全边界研究参考 Anthropic 对不同产品采用不同隔离模式的经验，不能概括为一种技术适用所有场景。[How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)

团队候选实验：相同任务、资源约束、镜像与并发下，对比完整任务成本、P95 可工作延迟、恢复成功率及故障后的重复副作用；再决定现有社区投入是在探索不同负载，还是重复补齐同类能力。

| 记忆与上下文 | 污染、跨租户泄漏、来源丢失、删除后的派生内容如何处理？ | OpenViking、共享记忆 |
| 插件与工具 | 不可信插件/MCP/skill 的代码和返回内容分别能触及哪些资源？ | DeerFlow、DSH 生态 |
| 协作与恢复 | 错误是否跨 agent 传播；重试、回滚是否重复外部副作用？ | 四方向接口 |
| 验证与处置 | 如何测攻击成功、业务损失、误阻断、人工负担及撤销恢复？ | 横向评估 |

规划推断：安全既应有独立问题清单，也应成为每个方向的设计和验收条件。是否成立独立投入主线取决于用户、威胁模型和可验证差异。沙箱隔离不等同于语义授权正确，插件可替换也不等同于安全隔离。

## Sandbox

公开进展：AgentENV 当前强调 agentic RL 环境规模、镜像按需加载、增量快照、fork 与资源密度；CubeSandbox 强调快速启动、快照回滚、跨节点恢复及出网凭证代理。上述性能数字是项目自报，不能跨项目直接比较。[AgentENV](https://github.com/kvcache-ai/AgentENV)、[CubeSandbox](https://github.com/TencentCloud/CubeSandbox)

E2B 的 SDK 已提供暂停与快照接口；Modal 区分目录、文件系统和内存快照，内存快照仍标注 Alpha。它们展示了不同的状态与生命周期抽象，而非完全同等的恢复语义。[E2B SDK](https://github.com/e2b-dev/E2B/blob/main/packages/js-sdk/src/sandbox/index.ts)、[Modal snapshots](https://modal.com/docs/guide/sandbox-snapshots)

待研究的四条主线：

- 生命周期经济性：长时间等待模型、空闲、恢复及镜像多样性下的总成本；不只测冷启动。
- 执行状态语义：什么被快照、什么没被快照；文件、进程、外部系统副作用如何配合恢复。快照不自动撤销已发出的外部操作。
- 隔离与可用性：文件、网络、凭证和控制平面权限共同决定可执行边界；microVM 只是其中一层。
- 训练与在线负载差异：训练更关注批量环境、reset/fork 和吞吐；在线任务还关心持久工作空间、尾延迟与用户数据边界。两者能复用哪些基础设施需要测量。

安全边界研究参考 Anthropic 对不同产品采用不同隔离模式的经验，不能概括为一种技术适用所有场景。[How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)

团队候选实验：相同任务、资源约束、镜像与并发下，对比完整任务成本、P95 可工作延迟、恢复成功率及故障后的重复副作用；再决定现有社区投入是在探索不同负载，还是重复补齐同类能力。

## Memory / Context

OpenViking 将 memory、resources、skills 统一组织，采用文件系统式访问和分层上下文。Anthropic 的 context engineering 实践包括按需检索、压缩、笔记与隔离上下文。[OpenViking](https://github.com/volcengine/OpenViking)、[Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

五条问题主线：

1. 上下文供给：需要时能否以合适粒度取得有效信息；语义相关不等于对当前决策有用。
2. 经验提炼与迁移：从轨迹形成经验，同时保留适用前提，避免将偶然成功泛化。
3. 持续更新：冲突、过期、删除、并发写入、异步整理及新信息可见延迟。
4. 来源与信任：区分用户陈述、外部内容、工具证据和 agent 推断，追溯并撤销错误传播。
5. 收益评估：记忆问答更准确是否转化为真实任务表现，且能覆盖写入与整理成本。

ACE 研究上下文 playbook 的增量演进；MemoryAgentBench 将选择性遗忘纳入评估；VikingMem 和 MemForest 分别提供时间状态管理与记忆构建效率方面的研究线索。[ACE](https://arxiv.org/abs/2510.04618)、[MemoryAgentBench](https://arxiv.org/abs/2507.05257)、[VikingMem](https://arxiv.org/abs/2605.29640)、[MemForest](https://arxiv.org/abs/2605.23986)

LongMemEval-V2（2026-05）评估环境状态、工作流、陷阱和前提意识，说明评估范围已超出聊天事实回忆。但它使用预采集轨迹和固定 reader 的证据问答，不直接证明在线任务成功率。MINJA 则说明记忆污染可能跨会话影响后续行为；不能将该研究成功率套用为 OpenViking 的风险率。[LongMemEval-V2](https://arxiv.org/html/2605.12493v1)、[MINJA](https://arxiv.org/abs/2503.03704)

团队候选实验：无记忆、原始轨迹文件与搜索、结构化经验记忆三组对比；在未用于经验构建的新任务及发生变化的环境中测成功率、重复错误、成本与错误经验撤销。把 memory 组件诊断与端到端任务收益分开。

## Harness

行业问题包括跨上下文接续、故障恢复、工具与权限边界、完成判定、评估归因，以及模型升级后哪些策略应删去。Anthropic Managed Agents 分离 session 日志、harness 和 sandbox；其经验显示为旧模型添加的 workaround 可能随模型改进失去价值。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)

长任务工程经验强调增量工作与验证；生成者自评或独立评价器都需要检查准确性。[Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)

Harness-Bench（2026-05）在共享环境和预算下研究模型与 harness 配对，提示不能将最终能力全归因于模型。DeerFlow 已集成 sandbox、memory、skills 与 subagents；功能存在不代表跨组件可靠性已被证明。[Harness-Bench](https://arxiv.org/abs/2605.27922)、[DeerFlow](https://github.com/bytedance/deer-flow)

团队候选实验：固定模型，注入工具超时、进程退出、上下文压缩、环境重建等故障，检查实际产物、恢复后约束保留和重复工作；更换模型后做策略消融，识别过时策略。

## Multi-agent

关键问题是任务结构与协调方式是否匹配。可独立广度搜索有实践收益；紧耦合和强共享状态工作可能承担较多沟通成本。Anthropic 的 research 系统案例不能单独证明纯拓扑收益，因为配置和计算投入也不同。[Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)

Towards a Science of Scaling Agent Systems v3（2026-04）在 260 个配置、6 个基准下显示协作效果依任务而异；工具密集型任务开销、单 agent 能力饱和及错误传播都是重要变量。MAST 将协作失败分成设计、agent 间不一致、验证与终止等类别。[Scaling Agent Systems](https://arxiv.org/abs/2512.08296v3)、[MAST](https://sites.google.com/berkeley.edu/mast)

团队候选问题：什么时候委派、给谁、传递什么上下文、如何协调写入、如何识别没有进展、何时停止或退回单 agent。

实验基线：普通单 agent、增加预算的单 agent、多 agent；分别比较等成本、等时间、等质量，区分并行加速、上下文隔离、专业能力与单纯增加计算的收益。

## 跨方向的评估基础

AgentCompass 将 benchmark、harness、environment 分开。Anthropic 的环境噪声研究表明，资源配置能影响 agentic benchmark 成绩，因此必须记录环境和资源执行策略。[AgentCompass](https://arxiv.org/abs/2607.13705)、[Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)

建议统一任务与轨迹、成功标准、模型版本、预算、环境配置、记忆历史与验收器；在重复运行中做消融和故障归因。已有基础可复用，不预设要新建一个框架。

## 待讨论的规划假设

以下均为研究后的候选方向，未形成团队共识：

- 可恢复且可验证的长任务执行：跨 sandbox 与 harness，以中断后仍正确交付为目标。
- 有效且可纠错的经验积累：跨 OpenViking 与实际 harness，以新任务收益及环境变化后的适应为目标。
- 按任务结构分配协作与预算：跨 multi-agent、harness、sandbox 分叉和共享知识，以同预算净收益为目标。

关键接口假设：sandbox 恢复不能使 session 和记忆仍指向未来状态；分支经验写入共享记忆应保留适用范围与证据；任务完成需要外部验收支撑。这些是建议验证的问题，不是已经证明的产品缺陷。
